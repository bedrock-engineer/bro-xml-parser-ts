# v0.4.0 — XSD-driven schema codegen

Status: proposal / planning
Author: design notes captured 2026-09-17

## Motivation

Everything through v0.3.0 was **hand-authored**: xpaths, result types, and resolver
wiring, kept in sync by hand across three-to-four files per field (type in
`src/types/index.ts`, binding in `src/schemas/*.ts`, sometimes a resolver, plus
the barrel exports in `node.ts`/`browser.ts`). That manual three-way sync is the
root cause of the bugs we actually hit:

- BHR-GT rock layers were silently dropped (a required field a human forgot).
- BHR-G never extracted `deliveryAccountableParty` despite it being in the data.
- New types repeatedly missed their barrel exports and their doc group.

The BRO XSDs are the authoritative, closed set of every property. We already
built the hard half of a generator to *check* against them — `scripts/check-xsd-coverage.ts`
fetches the XSDs, follows imports, unwraps GML PropertyType wrappers, collapses
partial dates, and flattens each registration object to typed leaf paths with
cardinality. The idea for v0.4.0: **turn that flattener into a code generator**,
so the mechanical parts are generated and stay in lockstep, and we hand-write
only what genuinely needs a human.

## Aside: why aren't the types just inferred from the schema objects?

The deeper miss predates the XSD idea. The schema object *could* have been the
single source of truth (the zod pattern) — the thing that blocked it is that
`ResolverFunction` is typed `(value, ctx) => unknown`. Returning `unknown` throws
the per-field output type away, so there is nothing to infer, which is what forced
hand-written interfaces and the manual type↔schema sync that produced the drift
bugs.

Had resolvers been generic, the whole result type would infer for free:

```ts
type Resolver<T> = (value: string | null, ctx: ResolverContext) => T;
type Field<T> = { xpath: string; resolver?: Resolver<T> };
type Infer<S> = {
  [K in keyof S]: S[K] extends { resolver: Resolver<infer T> } ? T : string | null;
};

const CPT_SCHEMA = {
  broId:      { xpath: "brocom:broId" },                    // string | null
  finalDepth: { xpath: "...", resolver: parseFloat },       // number | null
  data:       { xpath: "...", resolver: processCPTResult }, // CPTMeasurement[]
} satisfies Record<string, Field<unknown>>;

type CPTData = Infer<typeof CPT_SCHEMA>; // one source, zero drift
```

So inference was always possible; the loose `unknown` typing just made it
impossible without a redesign.

**But inference is not a pure win for a library that ships docs** (this one does —
see the TypeDoc setup). TypeDoc can't render `type CPTData = Infer<typeof CPT_SCHEMA>`
as a clean page: you lose per-field JSDoc, readable hovers/error messages, and a
stable reviewable public API surface. That is exactly why mature schema libraries
still *ship* explicit `.d.ts` even when they infer internally — they generate the
types rather than expose the inference.

There are three single-source designs; inference is the middle one:

| approach | source of truth | drift? | coverage guaranteed? | docs quality |
| --- | --- | --- | --- | --- |
| Hand-write both (through v0.3.0) | none | yes | no | good |
| Infer from a typed schema | schema | no | **no** — only "type matches what I typed" | poor |
| **Generate from the XSD** | XSD | no | **yes** | good (emit real interfaces + JSDoc) |

The point: inference fixes drift but only guarantees the type matches *the schema
you hand-wrote* — it cannot tell you the schema is missing a field the XSD has,
which is the exact bug class we spent v0.3.0 chasing. Generating from the XSD gives
the same no-drift single source **plus** completeness **plus** clean emitted
interfaces with doc comments. So the conclusion isn't "we should have inferred" —
it's "there should have been one *generated* source, and the XSD is the better
generator input than the schema." Typing the resolvers to enable inference is the
cheaper 80% fallback if the generator isn't built yet.

## What gets generated vs hand-written

Generated (from the XSD, committed to the repo like `codegen:reference-codes`):

- The **scalar `SchemaField` entries** — `xpath` + a resolver guess from the XSD
  base type (`date`→`parseDate`, `decimal`/`double`/`Measure`→`parseFloat`,
  `boolean`→`parseBoolean`, `integer`→`parseInt`, else string).
- The **scalar fields of the result type** (a generated base interface).

Hand-written (unchanged — codegen never touches these):

- The semantic resolvers: `<values>` CSV blob, GML geometry → `{x,y,epsg}`,
  partial-date collapse, sentinels (`-999999`/`NaN`), nested arrays/objects
  (fractions, determinations, intervals, rock description).
- The complex result types (discriminated unions, nested structures).
- The schema bindings for those complex fields.

The two compose cleanly because `Schema` is `Record<string, SchemaField>` (spread)
and interfaces extend. This already works — see `...COMMON_REGISTRATION_FIELDS`.

```ts
// generated: src/schemas/generated/cpt.generated.ts
export const CPT_SCALARS: Schema = { /* xpath + resolver guesses */ };
export interface CPTScalars { /* generated scalar fields */ }

// hand-written: src/schemas/cpt-schema.ts
export const CPT_SCHEMA: Schema = {
  ...CPT_SCALARS,
  data: { xpath: "...", resolver: measurementResolvers.processCPTResult },
  dissipationTests: { xpath: "...", resolver: ... },
  registrationHistory: { xpath: ".", resolver: processRegistrationHistory },
};

// hand-written type extends the generated scalar base
export interface CPTData extends BRORegistrationObject, CPTScalars {
  data: Array<CPTMeasurement>;
  dissipationTests: Array<DissipationTest>;
  // ...complex fields only
}
```

## The one thing codegen can't do: names

Our public field names are **curated**, not mechanical: `deliveredVerticalPositionOffset`
(not `offset`), `cptType` (not `conePenetrometerType`), flattened out of deep
paths. A generator can't invent those, so the residual hand-authored artifact is
a committed **path → friendly-name (+ optional resolver override)** map per domain:

```ts
// src/schemas/generated/cpt.map.ts  (hand-maintained)
export const CPT_NAME_MAP = {
  "brocom:broId": "broId",
  "./dscpt:deliveredVerticalPosition/cptcommon:offset": "deliveredVerticalPositionOffset",
  // paths omitted here are resolver-owned or intentionally skipped
};
```

This is the honest trade: we don't get Python-`xsdata`'s "free everything" because
we chose ergonomic names over mechanical ones. We get **free xpaths, free
resolver-type guessing, and generated type↔schema that can't drift** — most of the
value, minus name invention.

## Ownership / exclusion

The generator must know which subtrees a resolver owns (so it doesn't emit
duplicate/competing scalar entries) and which are deliberately unmodeled. That
config already exists conceptually in the checker:

- `resolverHandledPrefixes` — subtrees a resolver reads dynamically (e.g. the CPT
  `<parameters>`/`<values>` measurement columns).
- `unmodeledPrefixes` — deliberate scope boundaries (e.g. BHR-G
  `boreholeSampleAnalysis`).

Reuse the same lists: anything under them is skipped by codegen; anything else
with no name-map entry is a hard error ("new XSD leaf, decide: name it, or mark
it resolver-owned/unmodeled"). That turns the current *report* into a *build gate*.

## What we already have vs what this adds

`check-xsd-coverage` already gives the **safety guarantee** — CI fails when the
XSD drifts from what our source references — for ~0% refactor. That's most of the
benefit. Codegen adds, on top: stop hand-typing xpaths, and keep type↔schema in
lockstep by construction.

## Rollout (incremental, low-risk)

1. Extend the checker into an **emit mode** (`npm run codegen:schema`) that writes
   `*.generated.ts` (scalars schema + scalar type) per domain, driven by the
   name-map + exclusion lists. Follow the committed-output pattern of
   `codegen:reference-codes` (generated files are reviewed and committed, not
   built on the fly).
2. **Prove it on SFR** (`dssfr/2.0`, currently unmodeled, ~147 leaves). Clean
   slate, no migration risk: write the SFR name-map, generate its scalar
   schema+types, hand-write its handful of resolvers. This also finally models
   SFR — real user value, not just plumbing.
3. If the ergonomics are good, **backport** CPT / BHR-GT / BHR-G one at a time.
   Each is a mechanical, spread-compatible swap (replace the scalar entries with
   `...DOMAIN_SCALARS`, extend the generated base type). Do them independently; no
   big-bang rewrite.
4. Wire `codegen:schema` + `check:xsd-coverage` into CI.

## Scope for v0.4.0

Minimum: the `codegen:schema` tool + **SFR modeled through it**.
Stretch: backport one existing domain (BHR-GT is the richest test) to validate the
migration path end-to-end.

This is likely another minor with breaking changes (new SFR types; possibly small
shifts if backported domains regenerate field ordering/optionality) — same 0.x
"breaking → minor" policy as v0.3.0.

## Non-goals

- Do **not** rewrite the working domains just to prove the generator. Let the next
  domain (SFR) pay for it; backport only if it clearly earns its keep.
- Do **not** try to auto-derive friendly names from XSD element names — the curated
  API is a feature; keep the name-map explicit.
- Do **not** generate resolvers. The semantic transforms (CSV/GML/partial-date/
  nested structures) stay hand-written; that's the part with real judgment in it.
